# 기획 및 MVP 기준

## MVP 목표

부산 공연 관람 전후의 여행 일정을 생성·편집하고, TourAPI 장소 검색과 AI 일정 생성을
지원하며, Fan Route 커뮤니티에 공유한다.

## 도메인 책임

| 도메인 | 주요 책임 |
| --- | --- |
| 사용자·인증 | Google OAuth, 프로필, 사용자별 AI 추천 횟수 |
| 공연 | 공연·공연장 정보와 공연장별 추천 장소 |
| 일정 | 여행 계획, 숙박, 날짜별 일정, 일정 항목, AI 일정 생성 |
| 장소 | TourAPI 장소 검색·동기화 |
| 커뮤니티 | 정보 공유·참고 루트·동행 모집, 좋아요, 댓글 |
| 채팅 | 동행 모집 채팅방 생성·채택 기반 참여, 메시지·읽음 처리 |

## 일정 정책

- 여행 계획은 공연 없이도 생성할 수 있다.
- 숙소는 여러 개를 등록할 수 있으며 체크인·체크아웃 일자를 가진다.
- 숙소 설정 화면은 여러 숙소를 편집한 뒤 목록 전체를 저장한다. TourAPI 숙소를 선택한 경우에는
  해당 장소의 좌표를 스냅샷으로 저장하고, 직접 입력한 숙소명·주소는 카카오 로컬 API로 주소 검색 후
  좌표를 저장한다. 조회 실패는 숙소 저장을 막지 않으며, 좌표 없는 숙소는 거리 기반 AI 앵커에서 제외한다.
- 여행 스타일은 일정 생성 후 별도로 저장하며, 여행 강도·복수 동행·여행 MBTI를 포함한다. 여행 강도는
  `RELAXED`/`TIGHT`, 동행은 `친구`·`연인`·`혼자`·`부모님`·`아이`, 여행 MBTI는 프론트에 확정된 9종
  (`맛집탐방형`·`감성사진형`·`역사문화형`·`자연힐링형`·`쇼핑집중형`·`카페투어형`·`액티비티형`·`로컬체험형`·`공연몰입형`)의 enum으로 관리한다.
  API 응답은 한국어 라벨을 사용하고, 기존에 저장된 같은 한국어 값도 호환해 읽는다.
- 관리자는 공연장 주변 장소를 컬렉션(명소·식당·카페 묶음)으로 등록한다. 같은 장소도 여러
  공연장·컬렉션에서 재사용할 수 있으며, 컬렉션 항목은 장소 ID를 참조한다.
- 공연장 주변 장소는 카테고리별로 미리 선정해 재사용 가능한 컬렉션으로 묶을 수 있다.
  컬렉션은 확정 일정이 아니라 사용자가 개인 일정에 가져다 쓸 장소 후보 묶음이며, 로컬 운영
  도구가 구성한 결과를 내부 반영 API로 저장한다.
- 로컬 운영 도구는 장소 후보를 조합해 공연을 제외한 최대 5개 장소의 일정 템플릿을 만들 수
  있다. 사용자가 템플릿을 선택하면 장소 항목이 개인 일정에 복사되며, 복사된 항목은 템플릿과
  독립적으로 수정·삭제할 수 있다.
- 장소의 성격은 허용된 enum 태그로 `place_tags`에 관리한다.
- 장소 컬렉션 조회 API(`GET /venues/{venueId}/place-collections`)는 공연장에 미리 구성한
  컬렉션과 항목을 반환한다.
- 사용자는 컬렉션에서 장소를 하나씩 골라 자기 일정에 추가하고 시각은 직접 정한다. 사용자가 공연을
  기준으로 주어진 여행 기간 사이에 원하는 장소를 채워 넣는 것이 전부이며, 코스로 묶거나 공연
  회차 시간대에 맞춰 자동으로 정렬·제외하는 로직은 두지 않는다.
- 이렇게 추가된 항목은 공연 연결 고정 항목이 아니라 **일반 일정 항목과 동일하게 수정·삭제**할
  수 있다.
- 선택한 공연장에 추천 장소가 없어도 별도 폴백 없이 빈 결과를 반환한다. 클라이언트는
  수동 일정 추가로 안내한다.
- 추천 장소 추가는 일정 소유권과 여행 계획의 공연장 일치를 검증한다. 공연 없이 생성된 여행
  계획에는 추천 장소를 추가할 수 없다.
- AI 일정 생성은 429·5xx·network timeout 같은 일시 오류만 지수 backoff로 재시도하고,
  JSON·장소·시간 검증 실패는 최종 실패 처리한다. 처리 중에도 수동 일정 추가를 막지 않는다.
- AI는 한국 시간(`Asia/Seoul`) 기준 당일 도착·출발 범위와 기존 일반 일정의 시간을 입력받는다.
  저장 직전에 최신 기존 일정과 생성 항목 사이의 체류시간 겹침을 검증하며 자정을 넘기는 결과는
  저장하지 않는다. 종료와 다음 시작이 같은 경계는 허용한다. 기존 일정에 시각이 없으면 시간
  검증에서 제외하고, 체류시간만 없으면 알려진 시작 시점만 보호한다.
- AI 일반 일정은 `TIGHT` 최대 5개, 그 외 최대 3개이며 체류시간은 1~720분이다. JSON 스키마와
  서버에서 함께 검증한다. 모델 응답이 정상 종료(`STOP`)되지 않았으면 저장하지 않는다.
  `placeId=null`인 일반 사용자 입력형(`CUSTOM`) 일정은 기존과 같이 허용한다.
- 비공연일 AI 일정 생성은 같은 여행 계획의 모든 날짜에서 이미 등록한 장소를 제외한 좌표 보유 장소를
  후보로 삼는다. 다른 여행 계획에서는 같은 장소를 다시 사용할 수 있다. 당일 숙소
  좌표가 있으면 20km까지 거리 점수(최대 60점)를 선형으로 주되, 먼 장소도 후보에서 제외하지 않는다.
  여행 MBTI 태그(25점), 동행 태그(15점)와 합산해 상위 10개만 Gemini에 보낸다. 숙소 좌표가 없으면
  거리 점수 없이 태그 점수로 정렬한다.
  후보 재선별 호출은 두지 않고 Gemini 일정 생성은 한 번만 호출한다. 도로 이동시간·인기도는 아직
  계산하지 않는다.
- AI 입력에는 후보 장소의 카테고리·태그·좌표와 후보 점수화에 사용하는 숙소 좌표를 함께 제공한다.
  좌표로 도로 이동시간을 확정하거나 미수집 영업시간을 추측하지 않는다.
- 사용자는 AI 추천을 누적 5회까지 사용할 수 있다. 실패한 AI 생성과 취소된 대기 작업은
  횟수를 사용하지 않는다.
- AI 일정 생성 요청은 작업 ID를 즉시 반환하고 백그라운드에서 실행한다. 클라이언트는 작업 상태 조회 API로 완료·실패를 확인한다.
- KOPIS의 `dtguidance`(공연시간 안내) 원문은 공연 정보에 그대로 보존한다. 모든 구문을 신뢰성 있게
  해석할 수 있는 경우에만 공연 기간의 실제 날짜별 회차로 전개하며, 일부만 해석된 결과는 저장하지
  않는다. 파싱 실패 시 임의의 공연 시각을 생성하지 않고 사용자에게 시간 확인이 필요함을 표시한다.
  자동 생성 회차와 관리자 등록 회차는 출처를 구분하며, 재동기화는 자동 생성된 미확정 회차에만
  적용한다. 회차 번호는 공연 전체가 아니라 같은 공연일 안에서 시간순으로 부여한다.

## 커뮤니티 MVP 결정

동행 모집 게시글을 만들면 채팅방과 방장 참여 정보를 같은 트랜잭션으로 생성한다. 방장은
해당 게시글의 최상위 댓글 작성자를 채택해 채팅방에 참여시킨다. 활성 참여자 수는 모집 정원을
초과할 수 없으며, 채택·재채택은 동시 요청에서도 정원을 넘지 않도록 직렬화한다. 메시지는
PostgreSQL에 저장하고, 단일 EC2 MVP에서는 Spring 내장 WebSocket(STOMP) 인메모리 브로커로
활성 참여자에게만 전달한다. 각 참여자의 마지막 읽은 메시지 ID는 REST로 갱신하고, 변경된
읽음 커서는 같은 방의 활성 참여자에게 실시간 전달한다. DIRECT/GROUP 채팅, 이미지 첨부,
메시지 수정·삭제는 후속 범위다.
동행 모집 게시글 삭제 시에는 연결된 MVP 채팅방·참여 정보·메시지도 함께 삭제한다. 종료 후
대화 이력 보존과 `closed_at` 기반 보관 정책은 후속 범위다.

## 알림 MVP 결정

- 채팅 메시지 수신자별 인앱 알림을 저장하고 알림 목록과 미읽음 수를 제공한다.
- FCM 디바이스 토큰은 사용자별로 여러 개를 등록할 수 있다. Firebase 설정이 준비된 환경에서만
  등록 토큰으로 푸시를 발송하며, 설정 누락이나 발송 실패는 메시지 저장·실시간 수신을 실패시키지 않는다.
- Firebase 서비스 계정 JSON은 저장소에 넣지 않고 `GOOGLE_APPLICATION_CREDENTIALS`가 가리키는
  배포 환경의 파일로만 제공한다. 운영 배포에서는 SSM SecureString
  `/troadie/firebase-service-account`에서 EC2 `/opt/troadie/secrets/`로 내려받는다.
