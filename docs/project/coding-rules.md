# 코딩 규칙

## 기준

이 문서는 저장소 `AGENTS.md`의 실행 규칙과 회의록에서 합의한 구현 관례를 팀 문서로
정리한 것이다. Notion에 참조된 별도 Coding Guidelines 문서는 현재 연결 권한으로 본문을
조회하지 못했으므로, 확인되면 이 문서와 `AGENTS.md`를 함께 갱신한다.

## 구현 원칙

- 변경 전 요구사항과 관련 문서를 확인하고, 비자명한 작업은 계획과 성공 기준을 먼저 공유한다.
- 필요한 최소 변경만 수행하고 관련 없는 리팩터링을 하지 않는다.
- 기존 도메인 패키지 구조, `BaseTimeEntity`, 보호 생성자, 정적 `create` 팩터리 패턴을 따른다.
- 새로운 동작에는 실용적인 범위의 집중 테스트를 추가하고 관련 검증을 실행한다.
- 실행할 수 없는 검증은 이유를 이슈 또는 PR에 남긴다.

## DTO 및 객체 매핑

- DTO는 도메인별 `dto` 패키지에 둔다.
- 도메인당 DTO 파일 하나를 사용하고, 요청·응답·하위 모델은 해당 파일의 중첩 `record`로
  구성한다. 예: `TripPlanDto.CreateRequest`, `TripPlanDto.Response`.
- DTO에는 Lombok Builder를 사용하지 않는다.
- 객체 매핑은 우선 정적 팩터리 메서드 또는 DTO 팩터리로 직접 작성한다. MapStruct는 매핑이
  복잡해져 명확한 이점이 있을 때만 팀 합의 후 추가한다.
- 엔티티는 보호 생성자와 정적 `create` 팩터리를 사용하며, 서비스 계층이 영속화와 도메인 간
  조합을 담당한다.

## API 및 데이터 규칙

- 컨트롤러 변경 시 Swagger/OpenAPI 문서를 함께 갱신한다.
- API 날짜·시간은 ISO-8601을 사용하고 서버·DB는 UTC로 저장한다.
- 인증이 필요한 API에만 `bearerAuth` 보안 요구사항을 추가한다.
- 환경 변수·비밀값을 코드에 넣지 않는다.

## 문서와 확인

- 기능·정책 변경 시 `docs/project/`의 관련 문서를 함께 갱신한다.
- ERD, 와이어프레임, 기획 문서, API 계약의 충돌은 이슈 또는 PR에 기록한다.
- 공유 계약에 영향을 주는 결정을 구현하기 전 관련 담당자 또는 팀의 확인을 받는다.
